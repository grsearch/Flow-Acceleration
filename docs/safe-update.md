# 受控升级：先预检，再停止，最后只启动一次

`deploy/safe-update.sh` 是 Linux/systemd 专用入口。默认只读；仅加 `--apply` 才停止已核验的 unit、fast-forward 当前检出、启动一次。它不连接 Git 远端，不处理冲突，不安装依赖，不重置或覆盖本地修改，不发送额外 kill，不迁移或回滚数据库。

## 使用范围与首次启用

首次部署这些保护措施须由运维完成：本入口及 helper 必须已经在生产的受审查版本内，systemd 有效配置必须为 `KillMode=mixed`、`KillSignal=SIGTERM`、`SendSIGKILL=no`，且停止超时在 120–900 秒之间（模板为 180 秒）。脚本不会自动修改 unit，也不会通过强杀来完成停止。

本地模板修改不会自动保护生产。旧 unit 没有 `SendSIGKILL=no` 时仍可能按 systemd 默认行为在停止超时后强杀；必须人工应用并重新加载 unit，再读取有效属性确认，才能认定生产启用了这些保护。

这是一条保守的代码更新路径：依赖清单/锁文件、`src/data/`、数据库迁移、部署脚本/unit、`.env`、存储设置或端口有变化时，预检拒绝并要求人工部署。因此包含这些文件的本次保护改动本身也必须人工部署一次，不能用新脚本绕过自己的门禁。

人工部署同样应先检查真正的 service/PID/工作目录和生产改动，准备目标版本，再执行正常停机；存在停止失败或残留进程时，继续排查。生产本地修改应保留并审查，不能以 reset/强制 checkout 消除。

`install.sh` 的首次文件复制不会复制 `.git`。这种安装目录不具备可验证的 Git 历史，不能直接使用本升级入口。应先由运维准备独立、完整的正式检出，核对审核提交及现有配置/数据路径，完成受控迁移；不能在原目录随意 `git init`、伪造 HEAD 或取消完整性检查来获得通过。

## 命令

先由运维将审核过的目标提交获取到生产仓库；脚本不执行 fetch。必须使用完整的 40 或 64 位小写提交哈希，不能写分支名。以下路径和哈希均为占位示例，按服务器实际信息替换：

```bash
sudo NODE_BIN=/absolute/path/to/node bash deploy/safe-update.sh \
  --project=/absolute/path/to/project \
  --unit=flow-acceleration.service \
  --expected-commit=0123456789abcdef0123456789abcdef01234567
```

预检成功并审核输出后，用同一命令追加 `--apply`。读取完整 `/proc`、确认数据库文件描述符归属也需要 root 权限；Git 命令会以 unit 的 `User` 执行。`NODE_BIN` 必须与运行中主进程使用的 Node 路径相同，版本不低于 22。启动验收默认最多 600 秒，可用 `--accept-timeout=900` 调整；范围为 60–900 秒，以便容纳历史数据较多时的冷启动。

运维必须先显式开启现有停开新单开关，使配置指定的 `data/LIVE_TRADING_DISABLED`（或 `project/data/` 内配置指定的其他普通文件）存在。脚本既不会创建它，也不会在结束后删除它。预检要求实际活动仓位、异步交易动作、未决订单、Mint 入场锁都为零，订单/锁缓存分别不超过 90/120 秒，且数据库三类待写队列为零、当前连续写错为零。旧版本没有这些证据时安全拒绝，不能将缺失字段理解为零。存量仓位应先由既有退出规则完成，升级后是否恢复开新单由运维另行决定。

三项策略定义必须保留，但不要求三个都能开新单。入口会从目标提交的实际配置推导 `enabled !== false` 的策略集合以及其中 `entryEnabled !== false` 的入场集合，允许目标入场集合为空；启动后必须与运行时集合逐项完全一致。关闭三个策略的新入场、保留 `enabled` 与退出规则是可验证的正常状态。输出会显示目标入场集合的数量和 ID，不会为通过验收而重新开启策略；全局停单哨兵也仍需保留。

明确限制：只支持规范化的绝对路径，路径字符限字母、数字、`_`、`.`、`-`、`/`；工作目录须为仓库根目录且归服务用户所有。unit 必须直接执行该 Node 和绝对路径 `src/index.js`，不支持 PM2、shell 包装或额外 Node 启动参数。

unit 环境仅支持 `Environment=NODE_ENV=production` 和一个必需的 `<project>/.env`。`.env` 必须为私有普通文件，采用无引号的单行 `KEY=value`，值不能包含空白、引号、反斜线或 `#`；不支持 `export`、多行、重复键或运行时预加载。这个限制使候选配置预检与 systemd 启动环境保持同一种解释；不符合时应人工部署，脚本不会重写凭据文件。所有环境值和底层命令错误内容均不输出。

## 检查与操作顺序

1. 读取 systemd 的真实 unit、MainPID、ExecStart、工作目录与 cgroup；核对 `/proc` 身份和运行环境。扫描进程，确认唯一收集主进程、研究主库及 raw 分片的唯一可写句柄归属；PM2 或无法完成归属扫描则拒绝。
2. 要求当前工作树无修改、无冲突/进行中的 Git 操作；除已验证的停开新单哨兵外，不允许未跟踪文件。目标提交已在本地且为当前 HEAD 的后继。子模块、受 Git 跟踪的符号链接、隐藏修改的 index 标志、自定义 Git 文件过滤器和 partial clone 不支持。重命名前后两个路径均检查，目标不能覆盖已存在的忽略文件。忽略规则内的生产 `.env`、数据库和日志正常保留。
3. 在内存读取目标提交，检查关键文件齐全、源码语法、静态引用可解析、已安装依赖版本符合声明以及 SQLite 原生模块与当前 Node 兼容。只加载配置与两个允许的纯计算配置模块，不启动业务程序或打开数据库；运行配置校验，并检查三策略和 HO500 的 0.1 SOL 桥接。当前磁盘与运行中的版本、配置也必须匹配。固定主数据库的实际路径、设备号与 inode，后续阶段发现换库即拒绝。
4. `--apply` 获取该入口的互斥锁后重新预检，执行一次 `systemctl stop`。只有正常退出码为 0、旧进程身份消失、unit cgroup 为空且不再有研究库 writer，才允许 `git merge --ff-only`。环境或 HEAD 在过程中变化也会停止升级。
5. fast-forward 以后再次检查磁盘版本和配置，然后执行一次 `systemctl start`。在设定的验收时限内只读轮询健康接口，核对新 MainPID/启动身份、提交、数据库路径、关键文件 `MATCH` 且路径无缺失/重复、三项策略定义及 HO500 桥接，并要求实际启用/可入场集合严格等于目标配置（可入场为零也可通过）。`lastPersistedTradeAt` 和 `lastFlushAt` 必须在新进程内连续增长，且持久化交易时间超过停止前。`observedTrades` 增长不算通过。这个验收不发送订单，也不改变交易开关。

停止、更新或验收任何一步失败都会退出并报告所处阶段，不会循环重启、回滚源码或回滚数据库。停止失败时旧进程可能仍然存在；更新后启动失败时检出可能已经处于目标版本；验收超时也可能只是没有新行情，不能据此杀进程。systemd 自身的 Restart 策略仍然生效；脚本检测到验收期间重新启动就报告失败，不追加重启动作。

脚本互斥锁只能防止它自己的并发执行。升级期间须避免其他管理员或自动化同时修改 unit、代码、环境或启动另一个收集实例。静态源码检查与依赖解析不能替代针对目标变更的测试和人工审查；部署前应先完成相应测试。

## 本地验证

```bash
node scripts/test-safe-update.js
```

回归用纯数据与模拟只读 Git 返回验证拒绝规则、配置载入、版本/持久化验收和 shell 操作顺序；存在 Bash 时还执行 8 个仅有模拟控制命令的流程场景，覆盖停止、残留进程检查、更新、复核、启动及验收失败，不会控制任何实际服务或读取生产数据库。Linux 上首次采用前还应在隔离的 systemd 测试实例演练正常停止、超时和残留 worker 情形。
